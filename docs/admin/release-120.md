# CajeerEngineBook 1.2.0 · Допуск, обновление и восстановление

**Production Auto Update Release** · операторское руководство для подписанного выпуска

[← Руководство администратора](README.md) · [Продуктовые изменения](../releases/v1.2.0.md) · [Все релизы](../releases/README.md)

> [!WARNING]
> **Исходный ZIP / архив изменений не является подписанным production-релизом.** Не применяйте его привилегированными средствами обновления. Для допуска нужны проверенная защищённая сборка `v1.2.0`, подписанные артефакты и отдельные испытания конкретной инфраструктуры.

## 1. Что входит в 1.2.0

Этот выпуск завершает интеграцию существующего пути **подписанный GitHub Release → поиск обновления → владелец установки → доверенный host-agent → Docker updater**. Это усиление рабочего механизма и регрессионных проверок, **не новый установщик**.

| Параметр | Значение |
| --- | --- |
| Book | `1.2.0` |
| PostgreSQL schema | `7` — без новой миграции |
| Встроенное ядро | `CajeerEngine 2.1.0` |
| Автоматическое применение обновлений | **Не поддерживается** |
| Обязательное окно обслуживания | **Да**, перед `Apply`, recovery, rollback |

### Усиление механизма обновлений

- SHA-256 отпечаток квалификации охватывает **все отслеживаемые файлы поставки**, включая Compose, Dockerfile, PHP, frontend, updater, зависимости, CI и тесты. Любое изменение инвалидирует старое evidence.
- Полное лабораторное подтверждение `full_qualification_verified` устанавливается только после проверки результатов жизненного цикла и настоящей **24-часовой** нагрузки. `production_certified=false` остаётся намеренно: лабораторная квалификация не сертифицирует чужую инсталляцию.
- Вывод host-agent ограничен **256 KiB stdout** и **1 MiB stderr** на операцию. При превышении лимитов или тайм-ауте процессная группа завершается, операция считается неуспешной.
- Сохраняются только **восемь** последних приватных диагностических заданий на хосте. Отдельный очищенный журнал операций при этом не удаляется.
- Тесты покрывают переполнение вывода, тайм-ауты, ошибки subprocess и несовпадение источников / evidence / отпечатков.

## 2. Обязательная квалификация выпуска

**Не переводите 1.2.0 в production**, пока защищённый тег `v1.2.0` не прошёл обязательные задания **того же CI run/attempt**, что и выпуск:

1. Нативные регрессионные проверки: доступ, импорт, ревью/публикация, аналитика, поиск и AI.
2. Независимое сканирование безопасности и зависимостей.
3. PostgreSQL/Redis и распределённый runtime, edge, Docker upgrade/rollback.
4. Физическая потеря данных, PITR и полный сценарий восстановления.
5. Выделенный **24-часовой** нагрузочный прогон.
6. Проверка соответствия исходников, commit, кандидата OCI и подписываемых образов; только затем — signing job.
7. Наличие полного набора опубликованных GitHub Release assets, SHA-256 inventory, evidence и проверяемых Cosign OCI-дигестов.

Нельзя повторно использовать результаты или подписи другой версии/commit. Даже подтверждённое прохождение лаборатории не заменяет тесты восстановления и maintenance fencing на рабочем хосте.

## 3. Подготовка к обновлению

Перед началом оператор должен зафиксировать состав установки: Compose project и overlay, число узлов/воркеров, БД и схему, версию, медиатома, конфигурацию TLS, используемые ключи и состояние агента обновлений.

- Создать **независимые** резервные копии Book data, PostgreSQL и WAL/PITR-репозитория, env/секретов, ключа проверки релиза, installer state (включая анти-downgrade high-water version) и root-agent state.
- Проверить реальное восстановление на отдельном одноразовом хосте; не полагаться на факт наличия файла backup.
- Получить официальный подписанный пакет `v1.2.0` и проверить подпись по **заранее независимо закреплённому Ed25519-ключу**. Не исполнять привилегированные инструменты из неподписанного source/patch ZIP.
- Согласовать изменения host-agent и updater, установить их совместно в root-owned каталог **вне** обновляемого дерева, проверить владельца файлов и права Unix-socket, затем перезапустить агент.

Подробнее: [подписанные артефакты](signed-releases.md), [резервирование и rollback](update-recovery-115.md), [аварийное восстановление](disaster-recovery.md).

## 4. Процедура перехода

| Этап | Что сделать | Условие продолжения |
| --- | --- | --- |
| **01 · Проверка** | В `/admin/updates` сверить версию, commit, changelog, схему и подписанный манифест | Релиз и ключ доверия совпадают; кандидат полный и совместимый |
| **02 · Fetch** | Загрузить пакет разрешённым действием | Пакет повторно проверен агентом; нет ошибок доверия |
| **03 · Preflight** | Проверить топологию, состояние хранилища и ограничения | Preflight завершён и изучен оператором; одной зелёной метки UI недостаточно |
| **04 · Maintenance fence** | Оградить входящий трафик, прямых клиентов и **все внешние записи** (включая remote workers, schedulers, PITR cycles) | Нет активных one-off Compose заданий, orphan containers и фоновых записей |
| **05 · Разрешение оператора** | Выпустить краткоживущее разрешение, привязанное к точному кандидату | Разрешение создано на доверенном хосте; само по себе оно **не** блокирует трафик |
| **06 · Apply** | Выполнить обновление через host-agent с проверкой подписей, backup, SQL-контракта, образов и health | Агент завершил операцию и сохранил квитанцию |
| **07 · Приёмка** | Проверить Book 1.2.0, owner login, OIDC, Reader, поиск, медиа, workers, Redis, историю обновлений | Всё работает; только теперь снова разрешаются вход и внешние записи |

> [!NOTE]
> При переходе **1.1.7 → 1.2.0** схема PostgreSQL остаётся **7**. Не запускайте не относящуюся к этому переходу SQL-миграцию. Подробное создание разрешения и ограждение трафика: [Secure Update Execution](update-execution-114.md).

## 5. Если что-то пошло не так

| Ситуация | Действия |
| --- | --- |
| **Fetch / Preflight не прошли** | Оставить работающую версию, проверить root-only логи, цепочку сертификатов, подписи, ключ и совместимость. После исправления причины безопасно повторить этап с тем же подписанным кандидатом. |
| **Apply завершился с ошибкой или был прерван** | **Не повторять** из браузера и не обнулять journal. Сохранить maintenance fence. Проверить `update.py status`, точный backup через `verify-backup --id` и следовать `update.py recover --offline` с требуемыми подтверждениями совместимости. |
| **Нужен rollback** | Выполняет только оператор хоста, имея предыдущий подписанный релиз и подтвердив совместимость данных, созданных после обновления. Откат создаёт новый backup, **не** возвращает историческое состояние SQL. |
| **Несовместимая или повреждённая SQL-база** | Не делать принудительный downgrade схемы. Использовать подтверждённый PITR / физическое восстановление по отдельной процедуре. |
| **Недоступен GitHub / внешний провайдер** | Показать явную ошибку или неполный статус, не заявлять «обновлений нет». Продолжать использовать текущий проверенный релиз. |

Если прервана миграция или активация, может потребоваться ручное восстановление данных. Точное поведение зависит от фазы сохранённой транзакции, версии и SQL-контракта.

## 6. Проверки на отдельном тестовом окружении

```sh
python3 tests/production-update-120.py
python3 tests/production-qualification-policy.py
python3 tests/release-signing.py
python3 tests/release-110-policy.py
sudo python3 tests/update-agent-114.py
python3 tests/update-manager.py
python3 tests/admin-docs.py
```

Запускайте тесты кода и безопасности **только на одноразовых данных**; для полного `tests/release-gate.py` нужны реальные Composer-зависимости, Docker, PostgreSQL/Redis и изолированная инфраструктура. Отсутствующий инструмент, тайм-аут или пропущенный job **не** считается успехом.

Для квалификации GitHub требуется доверенный выделенный self-hosted runner, полные 24 часа нагрузки SQL/Redis и evidence физического восстановления. После неё оператор должен отдельно выполнить drill на своей установке. Планировщик `notify_only`, `download_only`, `manual_approval` **не** активирует релиз автоматически; `Apply`, recovery, rollback, изменение схемы или топологии остаются ручными действиями.
