# Workspace analytics and consent — Book 1.0.5

This is an operational implementation, not a declaration-only integration. Book aggregates anonymous first-party page views and events per workspace; optionally loads Google Analytics 4 and Yandex Metrica (including Webvisor) after explicit consent. All capabilities are **disabled by default** and require a workspace administrator to enable them.

## Deploy / upgrade from Book 1.0.4

1. Back up **both** the installation state and PostgreSQL (if configured). Stop **all** web, worker, and domain-check nodes using the database, including other Book installations sharing that schema. Preserve the previous application image and the corresponding backup.
2. Apply the changed-files patch at the release root, keeping paths intact. Rebuild the PHP image so the local JavaScript, PHP classes, migration SQL and new templates are present everywhere.
3. **PostgreSQL users only:** on the writable PostgreSQL primary, with the operator migration credentials and other nodes stopped, run `php bin/migrations.php plan`, `php bin/migrations.php preflight`, `php bin/migrations.php apply --offline`, then `php bin/migrations.php verify`. This upgrades shared database schema **3 → 4** and creates the independent `cajeer_book.analytics_daily` table. Runtime code requires schema 4 and deliberately refuses to start before the migration; do not do a rolling mixed-version upgrade.
4. Verify `php tests/analytics.php`, `python3 tests/analytics-http.py`, then run the full project release qualification and your PostgreSQL/Redis/domain deployment gates. Restore traffic only after all required checks pass.
5. Go to **Workspaces → Analytics** (visible to workspace managers), enable collection and optionally specify a GA4 measurement ID (`G-...`) and/or Yandex Metrica numeric counter ID. Optionally enable Webvisor when a Yandex counter is set. Use actual IDs from accounts you own. The settings are independently stored, validated and revision-checked for every workspace, including an adopted legacy workspace.

## Visitor consent and data flow

On public Reader pages (`/`, `/search`, `/docs/...`) the browser loads only the local `analytics.js` until consent. On first visit, a banner offers **Accept analytics** and **Reject analytics**. The choice is saved in the browser's local storage **per workspace** (and browser origin). A **Privacy preferences** footer button allows changing or withdrawing it at any time. Global Privacy Control forces the page to start in denied mode. No analytics vendor script or first-party event request is sent while denied.

After acceptance, Book sends `{event,path,consent:true}` to the same-origin first-party POST endpoint `<workspace>/analytics/collect`, with no cookies or credentials. Only predeclared event names `page_view`, `search`, `link_click`, `download` and `feedback` are accepted. The server rejects unknown properties, query strings, fragments, traversal, data over 1 KiB, missing or cross-site Origin, and disabled/private workspaces. It stores **UTC daily aggregate counters** only. It never stores IP addresses, cookie IDs, usernames, full referrers, full URLs with queries, or page content. Browser extensions blocking third-party requests may still block GA4 or Metrica; first-party aggregation remains independent.

For GA4, the local integration uses **basic Google Consent Mode v2**: all relevant fields (`analytics_storage`, `ad_storage`, `ad_user_data`, `ad_personalization`) default to denied, and only analytics storage is granted after affirmative consent. The Google tag is inserted only after accepting; ad fields remain denied. `send_page_view` is disabled, and the application emits exactly one initial `page_view` itself. For Yandex, `ym(...,'init', {defer:true, ...})` is run only after accepting, followed by explicit `hit`. Supported application events call `ym(...,'reachGoal', name)`; configure matching goals in the Metrica dashboard if you want them counted as goals. `webvisor:true` is used only when an administrator enabled it and a visitor accepted. Google/Yandex receive their own network data according to their policies; Book's aggregate-only privacy guarantee applies to **Book's own counters**, not external services.

On withdrawal, the page sends a denied consent update to Google and reloads, dropping injected third-party scripts. If local storage is unavailable, the selected consent applies to the current page only and no analytics loads on a subsequent page without new permission. The implementation does not infer consent from an authenticated Book session, geography, or the existence of a counter ID. This feature does not replace a legal privacy notice or organizational compliance review.

## Scope and storage

- Each Workspace stores tracker settings in the versioned identity registry. Only members with effective `manage` permission may modify settings or access `/analytics?id=WORKSPACE_ID`; writes are CSRF protected and fail on stale revision.
- File installations persist daily JSON aggregates under the private `BOOK_DATA_DIR/workspaces/ORG/WORKSPACE/analytics` directory, or `BOOK_DATA_DIR/analytics` for the adopted legacy workspace, with locking, atomic writes, restricted file permissions and a bounded number of paths per day. The 30-day aggregate management report is independent of visitors' personal data.
- PostgreSQL installations use a dedicated upsert counter in `cajeer_book.analytics_daily`, keyed by installation namespace, workspace scope, UTC day, event and page path. All nodes must run schema 4. No Redis requirement. Connection/SQL errors are logged and reported as 503 for the collection request without breaking the underlying Reader operation.
- **Recovery caveat:** the current portable installation backup copies Book content and identity but does **not** include aggregate analytics data; PostgreSQL/PITR database backups include the SQL counter table. For file installations, include the private `analytics` directories in your separate filesystem backup if metrics must survive a full restoration. Never put them under `public/`.
- **Retention:** reports query the last 30 days. Older aggregate rows/files are not automatically purged in this release; set a retention policy and schedule trusted backup/cleanup jobs to meet your requirements. Do not interpret the 30-day report window as automatic deletion.

## Verification

Test with a new private workspace first. The public endpoint should return 404 when disabled; submitting without Origin or with a foreign Origin should return 403. Confirm that a fresh browser with no preference produces no requests to `google-analytics.com`, `googletagmanager.com`, `mc.yandex.ru` or the first-party `analytics/collect` endpoint until acceptance. Accept, navigate between published pages, submit search, and verify the 30-day Workspace report. Reject/withdraw and confirm that subsequent page loads do not send analytics. Repeat via the verified public custom domain and the legacy route if enabled. Respect ad blockers and do not bypass them.

For a PostgreSQL installation use `php bin/migrations.php status` to confirm schema 4. Schema 4 can be rolled back via the offline migrator only if `analytics_daily` is empty; the down migration deliberately refuses to delete nonempty counters. Export/preserve the data first if you intend to downgrade.
